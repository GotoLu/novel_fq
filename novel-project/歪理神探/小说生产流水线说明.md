# 小说生产流水线说明

创建日期：2026-06-05

## 一、目标

用 `novel-project/tools/novel_pipeline.py` 建立可长期运行的小说生成系统：

- 以 `08-全流程重构计划.md`、`重构进度表.md`、`42-新版全书完整大纲.md` 为路线图，自动识别当前应该执行的下一步。
- 根据路线图、章节卡、资产库、前文、评估和连贯性摘要生成下一轮任务包。
- 可选调用外部 LLM/Codex 命令生成章节。
- 无人值守模式下，每章按“章节卡 → 正文 → 评估 → 连贯性摘要/进度记录”四阶段执行，任何阶段缺产物都会阻塞。
- 每当生成尾数为 0 或 5 的章节后，先检查该五章段是否合格；默认审查通过后 checkpoint 退出，重新启动脚本以清空外部会话上下文。
- 用本地状态文件记录预算估算、上下文文件、产物和阻塞原因。

## 二、核心决策与依据

最优方案：采用“本地调度器 + 外部模型命令适配”的方式，而不是把模型 API、提示词和文件写入逻辑硬绑定。

依据：

- 可行性：当前仓库是文档型小说项目，已有全流程计划、全书大纲、章节卡、正文、评估和进度表，调度器能直接复用这些文件。
- 路线清晰：`08-全流程重构计划.md` 定义阶段链路，`42-新版全书完整大纲.md` 定义 100 章剧情边界，`重构进度表.md` 定义当前事实和下一步。
- 成本控制：脚本默认只生成提示包，不调用模型，避免误耗额度。
- 上下文控制：脚本按优先级读取规则、资产库、大纲、最近章节和评估，超过预算自动裁剪。
- 连贯性控制：每章完成后生成 `novel-project/.pipeline/continuity/第XXX章_连贯性摘要.md`，下一章优先读取，用来平衡人物状态、伏笔、案件进度和情绪债。
- 长期可恢复：状态写入 `novel-project/.pipeline/state.json`，失败时记录阻塞原因，方便下次继续。
- 风险可控：0/5 章触发五章闸门，避免连续生成导致结构性问题累积。
- 额度恢复：识别 `quota`、`rate limit`、`out of codex messages` 等额度/限流提示；能解析恢复时间则等到提示时间，不能解析则按 5 分钟轮询。

## 三、常用命令

只生成下一章提示包，不调用模型：

```bash
python3 novel-project/tools/novel_pipeline.py
```

指定章节生成提示包：

```bash
python3 novel-project/tools/novel_pipeline.py --chapter 28
```

强制做五章闸门审查提示包：

```bash
python3 novel-project/tools/novel_pipeline.py --chapter 30 --force-audit
```

接入外部命令并实际运行：

```bash
NOVEL_PIPELINE_LLM_COMMAND='你的命令 {prompt_file} {output_file}' \
python3 novel-project/tools/novel_pipeline.py --run --max-cycles 10
```

使用本地 Codex CLI 调度：

```bash
NOVEL_PIPELINE_LLM_COMMAND='env TERM=xterm-256color codex exec --cd /Users/luxd/workspace/testCode/novo-test1 -s read-only --output-last-message {output_file} -' \
python3 novel-project/tools/novel_pipeline.py --run --chapter 28 --max-cycles 5
```

也可以使用项目内封装脚本：

```bash
novel-project/tools/run_codex_pipeline.sh --chapter 28 --max-cycles 5
```

该封装脚本会自动设置：

```bash
NOVEL_PIPELINE_LLM_COMMAND='env TERM=xterm-256color codex exec --cd <项目根目录> -s read-only --output-last-message {output_file} -'
```

这里使用 `-s read-only` 是为了让 Codex 只输出 `### FILE:` 文件块，不直接改仓库文件；真正写入仍由 `novel_pipeline.py` 统一解析和落盘。

封装脚本默认附带 `--restart-after-audit`：尾数 0/5 五章闸门通过后，脚本会先 checkpoint，再重新 exec 自身，从下一章继续，以清空外部会话上下文。

默认 `--run` 是严格无人值守模式：每章必须生成章节卡、正文、评估和连贯性摘要。

若需要尊重进度表中的“只做准备/暂缓正文”，再额外加：

```bash
python3 novel-project/tools/novel_pipeline.py --run --respect-progress-gate
```

尾数 0/5 审查通过后，默认会停止以清空外部会话上下文。封装脚本 `run_codex_pipeline.sh` 会自动重新 exec 自身，从下一章继续；直接调用 `novel_pipeline.py` 时，需要显式添加 `--restart-after-audit` 才会自动重启。

如果确认外部命令是完全无会话上下文的，也可以连续跑过五章闸门：

```bash
python3 novel-project/tools/novel_pipeline.py --run --continue-after-audit
```

外部命令输出必须使用脚本约定的文件块格式：

```text
### FILE: novel-project/正文/第028章_消失的不是它_重构稿.md
正文内容

### FILE: novel-project/正文/第028章_消失的不是它_重构评估.md
评估内容
```

四阶段输出要求：

1. `card`：必须输出 `XX-第N章重构章节卡.md` 和计划核对。
2. `draft`：必须输出 `正文/第NNN章_章节标题_重构稿.md`。
3. `evaluate`：必须输出 `正文/第NNN章_章节标题_重构评估.md`。
4. `continuity`：必须输出 `.pipeline/continuity/第NNN章_连贯性摘要.md` 和进度记录。

## 四、预算与上下文机制

默认参数：

- `--context-tokens 24000`
- `--reserve-output-tokens 6500`
- `--daily-budget-tokens 120000`
- `--quota-poll-seconds 300`
- `--quota-max-wait-seconds 86400`

脚本会优先放入：

1. `08-全流程重构计划.md`、`重构进度表.md`、`42-新版全书完整大纲.md`。
2. 项目规则和创作质量优先级。
3. 资产库、人物压力测试、案件引擎。
4. 本章章节卡。
5. 最近三章连贯性摘要、正文和评估。
6. 五章闸门时额外放入该五章段正文和评估。

脚本判断下一步的顺序：

1. 优先读取 `重构进度表.md` 的“下一步”章节，提取当前应该生成的章节或任务。
2. 若用户用 `--chapter` 指定章节，则以用户指定为准。
3. 若进度表没有明确下一章，则回退到正文目录中最新完成章节的下一章。
4. 每轮提示都会要求模型先核对三份路线图，再决定是否生成正文、章节卡、评估或阻塞报告。

默认无人值守模式不会因为 `重构进度表.md` 写着“章节卡/正文准备”或“暂不批量正文推进”而跳过正文。只有显式使用 `--respect-progress-gate` 时，脚本才会把本轮视为准备态任务：

- 优先生成章节卡、写作策略和计划核对。
- 正文和评估可以暂缓，不会被脚本判为失败。
- 进度记录必须说明暂缓依据和下一步进入正文的条件。

当上下文超出预算时，脚本会保留文件头尾并裁剪中段。

上下文清空策略：

- 脚本本身不依赖聊天窗口上下文，只依赖文件和 `.pipeline/continuity/` 摘要。
- 每章只读取必要文件，不把全书全文塞进提示。
- 每到尾数 0/5 的章节并完成五章审查后，默认 checkpoint 退出；重新启动脚本即可用新外部会话继续下一章。
- 状态文件会记录 `last_success_chapter`，所以重启后不会重跑已完成章节。

额度/限流策略：

- 外部命令输出中出现 `quota`、`rate limit`、`too many requests`、`out of codex messages`、`message limit`、`429` 等内容时，脚本视为额度/限流。
- 如果错误里包含 `retry after 120 seconds`、`try again in 5 minutes`、`HH:MM` 这类恢复提示，脚本按提示等待后重试同一阶段。
- 如果没有明确时间，脚本每 5 分钟轮询一次。
- 如果等待超过 `--quota-max-wait-seconds`，脚本停止并记录断点；下次启动会回到同一章，并跳过已存在的前置产物。

## 五、0/5 章闸门

当章节号尾数为 0 或 5 时，脚本在生成该章后自动创建五章审查任务。

审查范围为该五章段，例如：

- 第 30 章：审查第 26-30 章。
- 第 35 章：审查第 31-35 章。

审查结论必须是“通过”或“有条件通过”，才建议进入下一章。

## 六、产物位置

- 提示包：`novel-project/.pipeline/prompts/`
- 模型原始输出：`novel-project/.pipeline/outputs/`
- 状态文件：`novel-project/.pipeline/state.json`
- 日志文件：`novel-project/.pipeline/pipeline.log`
- 五章审计：`novel-project/.pipeline/audits/`
- 进度更新：`novel-project/.pipeline/progress_updates/`
- 连贯性摘要：`novel-project/.pipeline/continuity/`

## 七、注意事项

- 脚本不会替代人工判断，质量闸门仍需按项目规则做证据化分析。
- 外部平台数据库查重不在脚本覆盖范围内，原创性结论只能写“项目内风险分型”。
- 第一卷审核结果未出前，若仍使用默认无人值守模式批量推进，脚本会按用户目标继续生成完整章节；若要按进度表暂停正文，必须使用 `--respect-progress-gate`。
- 三份路线图冲突时，脚本提示词规定：以 `重构进度表.md` 的当前状态和下一步为最近事实，以 `42-新版全书完整大纲.md` 的章节安排为剧情边界，以 `08-全流程重构计划.md` 的阶段链路为流程边界。
